# Agentic Loop: End-to-End Admission Flow Testing

You are an autonomous senior QA engineer and full-stack developer working inside this school management system.

Your task is to **test, diagnose, fix, and retest the complete admission flow across both the frontend and backend**.

Do not assume that an endpoint, page, form, or database operation works simply because it exists. Verify the complete business flow using the actual implementation in this repository.

---

## 1. PRIMARY OBJECTIVE

Test the admission lifecycle from beginning to end:

```text
Admission/Application
        ↓
Applicant Information
        ↓
Application Validation
        ↓
Application Submission
        ↓
Application Review
        ↓
Admission Decision
        ↓
Student Creation
        ↓
Student Enrollment
        ↓
Course/Programme Assignment
        ↓
Academic Year/Session Assignment
        ↓
Fee/Finance Assignment
        ↓
User/Account Creation
        ↓
Notifications
        ↓
Audit Logging
```

The exact flow must be determined from the existing project architecture and business logic.

Do NOT invent a new admission workflow if one already exists.

# 3. CREATE AN ADMISSION TEST MATRIX

Before testing, create a test matrix internally.

At minimum test:

### Happy paths

1. Create valid admission application.
2. Submit application.
3. Retrieve application.
4. Review application.
5. Approve application.
6. Verify student record is created.
7. Verify enrollment is created.
8. Verify programme/course assignment.
9. Verify academic year/session assignment.
10. Verify applicable fees are assigned.
11. Verify required user/account creation.
12. Verify notification generation.
13. Verify audit log.

### Validation failures

Test:

* missing required fields
* invalid email
* invalid phone number
* invalid dates
* invalid IDs
* invalid programme/course
* invalid academic year
* invalid academic session
* duplicate applicant
* duplicate admission
* duplicate student
* duplicate enrollment
* invalid admission status
* nonexistent related records
* unauthorized user
* insufficient permissions

### State-transition failures

Test invalid transitions such as:

```text
Rejected → Approved
Approved → Pending
Completed → Pending
Cancelled → Approved
```

if those transitions are not permitted by the business rules.

Never assume statuses are interchangeable.

---

# 4. DATABASE INTEGRITY TESTING

For every successful admission operation, inspect the database.

Verify:

### Applicant

* correct applicant exists
* no unintended duplicate applicant

### Admission

* correct admission/application record exists
* correct status
* correct timestamps
* correct references

### Student

If approval creates a student:

* exactly one student is created
* student references the correct applicant/admission
* student number is generated correctly
* required fields are populated

### Enrollment

Verify:

* exactly one enrollment where expected
* correct student
* correct programme/course
* correct curriculum
* correct academic year
* correct academic session
* correct status

### Fees

If admission triggers fee assignment:

* correct fee structure is selected
* correct fee items are attached
* correct academic year/session is used
* no duplicate fee assignments
* amounts are correct

### User

If the system creates an account:

* exactly one user is created
* correct role is assigned
* correct student relationship exists
* credentials/authentication state are correct
* password is never exposed in API responses or logs

---

# 5. TRANSACTION TESTING

Pay special attention to multi-table admission operations.

If admission approval performs:

```text
Admission update
+
Student creation
+
Enrollment creation
+
Fee assignment
+
User creation
```

verify whether these operations are transactional.

Simulate failures halfway through the process.

For example:

```text
Admission approved
↓
Student created
↓
Enrollment fails
```

Determine whether the system leaves inconsistent data.

The expected production-grade behavior is:

```text
BEGIN TRANSACTION

Admission update
Student creation
Enrollment creation
Fee assignment
User creation

COMMIT
```

or a correctly designed equivalent.

If a critical operation fails, verify rollback.

Do not silently accept partial admission state.

---

# 7. AUTHORIZATION TESTING

Test the admission workflow using different roles.

At minimum investigate the roles available in the project and test:

```text
Administrator
Admission Officer

```

Use the project's actual roles if different.

* who can create applications

Test the admission UI as a real user.

Verify:

* validation works
* invalid input is rejected
* valid input is accepted
* dropdowns load correct data
* dependent dropdowns work
* date fields work

### Submission

* incorrect field names

* missing error messages

---

# 9. API CONTRACT VERIFICATION

Compare frontend API calls against backend DTOs and responses.

For every admission request verify:

```text
Frontend field
        ↕
Backend DTO field
        ↕
Database field
```

Look for:

* renamed fields
* incorrect casing
* nullable/non-nullable mismatch
* string vs number mismatch
* date format mismatch
* enum mismatch
* nested object mismatch
* incorrect IDs
* incorrect response property names

Fix contract mismatches at the correct architectural layer.

Do not add unnecessary frontend hacks to compensate for incorrect backend contracts.

---

# 10. DUPLICATE AND IDEMPOTENCY TESTING

Repeatedly submit the same admission.

Test:

```text
Submit
Submit again
Refresh
Submit again
```

Determine whether duplicate records are created.

Where the operation should be idempotent, make it idempotent.

Where duplicates must be rejected, verify that the backend enforces uniqueness.

Do not rely exclusively on frontend checks.

Database constraints should protect critical uniqueness requirements.

---

# 11. CONCURRENCY TESTING

Simulate two admission officers attempting to approve the same application simultaneously.

Verify:

```text
Request A → Approve
Request B → Approve
```

Expected behavior should follow the business rules and must not result in:

* duplicate students
* duplicate enrollments
* duplicate fee records
* duplicate accounts
* inconsistent admission statuses

Check for race conditions.

If necessary, recommend or implement:

* database unique constraints
* transactions
* row locking
* optimistic concurrency
* idempotency protection

Use the approach appropriate to the existing architecture.

---

# 12. ERROR RECOVERY

Deliberately cause downstream failures.

Examples:

* invalid course ID
* unavailable academic session
* database constraint violation
* duplicate user
* fee configuration missing
* notification failure

Verify that the admission process handles the failure correctly.

Important:

A notification failure should not necessarily invalidate a successfully committed admission unless the business logic explicitly requires it.

Separate critical database operations from non-critical side effects where appropriate.

---


---

# 21. AGENTIC LOOP RULES

Operate autonomously.

Do not stop at the first error.

Do not merely report:

> "There is an error."

Instead:

1. Find the error.
2. Trace it to its source.
3. Determine whether it is frontend, backend, database, API contract, authorization, or business logic.
4. Fix it when the correct fix is clear.
5. Test the fix.
6. Continue testing the rest of the admission flow.
7. Re-run regression tests.

Do not rewrite working architecture unnecessarily.

Do not introduce new libraries unless there is a strong technical reason.

Follow the existing project's:

* coding conventions
* architecture
* naming conventions
* error handling
* authentication
* authorization
* database patterns
* UI patterns

---

# 22. STOP CONDITIONS

Do not declare success because:

* the page loads
* the form submits
* an API returns 200
* a database record exists

Declare the admission flow successful only when:

```text
Frontend works
        AND
API contract works
        AND
Backend business logic works
        AND
Database relationships are correct
        AND
Authorization works
        AND
Validation works
        AND
Duplicate protection works
        AND
Transactions/rollback behave correctly
        AND
Important audit events work
        AND
Errors are handled correctly
        AND
Regression tests pass
```

# EXECUTION DIRECTIVE

Start now.

First inspect the repository and identify the complete existing admission architecture.

Then build the admission test matrix.

Then execute the tests.

When you find a defect, fix it and continue the loop.

Do not stop after the first successful test.

Continue until the complete admission lifecycle has been verified end-to-end or until a genuine blocker prevents further testing.

The goal is not merely to find bugs.

The goal is to leave the admission workflow **verified, consistent, secure, transactional, and production-ready across frontend, backend, and database layers.**

2. IMPORTANT: Do not confuse API workers with background workers

This is the central architectural correction.

There are two completely different workloads.

API process

Responsible for:

HTTP requests
Authentication
Authorization

Validation
Business operations
API responses


Run the NestJS API as one process per container.

Background workers

Responsible for expensive/asynchronous work such as:

PDF generation
Bulk report generation
Email sending
Notifications
Large exports
Other long-running jobs


These should NOT block HTTP requests.

3. PDF generation

The system needs to support potentially large PDF workloads, including scenarios such as generating reports for approximately 2,000 students.

Do NOT generate thousands of PDFs synchronously inside an HTTP request.

Bad architecture:

POST /reports/generate
        |
        +--> generate PDF 1
        +--> generate PDF 2
        +--> ...
        +--> generate PDF 2000
        |
        +--> finally respond


Required architecture:

POST /reports/generate
        |
        +--> create job(s)
        |
        +--> return quickly
                |
                v
             Job Queue
                |
                v
           PDF Worker
                |
                v
           File Storage


The API should be able to tell the caller that processing has been queued/in progress rather than keeping the HTTP connection open for the entire operation.

Implement controlled concurrency.

Do NOT allow an administrator action involving 2,000 PDFs to spawn 2,000 simultaneous PDF-generation processes/tasks.

The worker must process jobs with bounded concurrency and support failure handling.
